# Hosted Forge setup (not deployed yet)

Forge currently runs locally unless both public Supabase variables are configured. Do not use the cloud mode until the private table and its RLS policies have been applied and tested with two accounts. The draft SQL is in [cloud-schema.sql](cloud-schema.sql); it has **not** been applied or security-verified.

Implementation status: local V2 validation, Google sign-in UI, optimistic cloud document updates, an account-scoped IndexedDB mutation queue, conflict detection, backup export, and confirmed import are implemented and covered by local tests. The live schema/RLS test, Google provider configuration, deployment, and phone-on-cellular acceptance test remain pending external access. The browser E2E suite has not completed cleanly in this workspace; do not use its partial output as a pass.

## Start here if you have not set up the providers

You need three accounts: [Supabase](https://supabase.com/dashboard) for private data and sign-in, [Vercel](https://vercel.com/dashboard) for the always-on website, and [Google Cloud](https://console.cloud.google.com/) for the Google sign-in client. Use accounts you control and enable MFA. Do not send project passwords, OAuth client secrets, or service-role keys in chat or commit them to this repository.

Create the Supabase project first. Choose a nearby region and keep the database password in your password manager. In **Project Settings → API**, locate the project URL and the **publishable** key; these are the two values the web build needs. Leave all secret/service-role keys out of Vercel's `VITE_*` variables. Do not apply the draft schema until we can run and verify the two-account RLS test.

Create a Vercel account and an empty project next. This repository currently has no Git remote; a direct [Vercel CLI deployment](https://vercel.com/docs/projects/deploy-from-cli) can link this folder without GitHub once you authorize the CLI. The first deployment can be local-only so you can learn the final `https://...vercel.app` URL before setting up OAuth. After the Google and Supabase configuration is complete, set the two public variables in **Vercel project → Settings → Environment Variables** and redeploy. Vite reads those variables at build time.

In Google Cloud, create a project and open **Google Auth Platform**. Set up the app's audience; if it is in testing mode, add your own Google account as a test user. In **Data Access**, request only `openid`, email, and profile. Create a **Web application** OAuth client. Add the Vercel origin (for example, `https://forge-name.vercel.app`, without a path) to **Authorized JavaScript origins**. In **Authorized redirect URIs**, paste the *exact* callback URL shown in **Supabase → Authentication → Providers → Google**. This is a Supabase URL, not the Vercel URL. Paste the resulting client ID and client secret into the Supabase Google provider page only. [Supabase's Google guide](https://supabase.com/docs/guides/auth/social-login/auth-google) has the current dashboard screenshots and field names.

Finally, in **Supabase → Authentication → URL Configuration**, set the Vercel HTTPS URL as the Site URL and add it to Redirect URLs. This must match the `redirectTo` origin the app sends. Add `http://localhost:5173` only if you want to test cloud sign-in on your computer. [Supabase's redirect URL guide](https://supabase.com/docs/guides/auth/redirect-urls) explains this allow-list.

1. Export a JSON backup from the existing local Forge app on each device. Keep both files before changing hosting or signing in.
2. Create a Supabase project and a Vercel project using accounts you control. In Supabase, create a CLI-named migration from the reviewed draft schema, apply it, and test that account A cannot select/update account B's row, anonymous clients cannot read rows, and an authenticated client cannot insert a forged `user_id`. Run Supabase Security Advisor. Do not put a service-role key in the web app.
3. In Google Cloud, create an OAuth **Web application** client. Configure the Supabase callback URL shown in Supabase Auth → Providers → Google as an authorized redirect URI. Configure the hosted Forge origin and `http://localhost:5173` as authorized JavaScript origins as required by Google's console. Put the Google client ID and secret **only** into Supabase's Google provider settings.
4. In Supabase Auth → URL Configuration, set the production Site URL to the Vercel HTTPS URL and allow that URL in Redirect URLs. If preview deployments must support sign-in, add only the needed preview URL patterns. Also allow the localhost URL for development.
5. Set Vercel environment variables `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from the Supabase project. These values are public browser configuration, not secrets. Never set `VITE_` variables to the Google client secret or a Supabase secret/service-role key.
6. Build with `pnpm build` and deploy the static Vite project to Vercel. Verify the final HTTPS URL and Google callback in the browser. On first sign-in, Forge creates a new default cloud document. In Settings, download its backup, review one existing browser copy or JSON backup, and explicitly make that copy canonical. Existing localStorage remains untouched.
7. Test on the phone using cellular data with the computer off. Sign into the same Google account on both devices, log a set offline on the phone, reconnect, and verify it appears on the computer. Also test a second account and a same-record edit conflict. Do not treat the app as ready until these checks pass.

Offline edits require one prior online sign-in in that browser. Pending edits live in IndexedDB and are not guaranteed to sync while the browser is closed. If the browser shows **Sync needs review**, export pending changes before modifying more data. Sign-out is disabled while pending edits exist. Export a cloud JSON backup regularly; cloud-provider backup availability depends on your plan.

Rollback: restore an earlier Vercel deployment for code issues. Before restoring data, export the current cloud document; importing an older JSON backup requires a current revision and explicit confirmation, so it cannot silently overwrite a newer copy.
